Notifi: plan

A clean-room Windows and Linux version of the Vorssaint Mac utilities. Tauri 2 + Rust. Covers all ~70 features, built in phases. Draft, 2026-10-20.

Read this first

  1. Clean room: builders never see Vorssaint's source code. They work only from the spec in spec/, written from Vorssaint's README, docs and screenshots. Notifi gets its own name, icon and look.
  2. Licence: MIT, since no GPL code is copied. Each spec file names where its facts came from.
  3. Stack: one Rust core with a platform layer (Windows, X11, KDE Wayland, GNOME Wayland). The UI is a web front end inside Tauri windows.
  4. GNOME on Wayland needs a small GNOME Shell extension (shipped with Notifi) for window moves, switcher thumbnails and focus-follows-mouse. KDE gets KWin scripts over D-Bus.
  5. Every Vorssaint feature is built. Nothing is dropped. Where a feature depends on something only Macs have (Dock, Spaces, notch, HDR headroom), Notifi builds the closest Windows/Linux version, marked ADAPT below. A parity checklist (spec/parity.md) tracks every Vorssaint feature against its Notifi spec.
  6. Same animation style as Vorssaint: Notifi copies the motion (timings, springs, how panels open, close and move) measured from Vorssaint running or from its videos. Name, icon, colours and branding stay Notifi's own. See section 2b.
  7. Two features are risky: fan control and temperatures on Windows need a kernel driver, and volume boost past 100% on Windows needs an audio driver (APO). Both are planned last and marked beta.

1. Clean-room process

  • Spec side (one agent plus you): reads Vorssaint's README, docs/*.md, changelog and screenshots, and watches the app run if you have a Mac. It writes one behaviour spec per feature in spec/<group>/<feature>.md: what the user sees, the settings, the shortcuts and the edge cases. No code, no file or type names from Vorssaint.
  • Build side (other agents): gets only spec/ and this plan. Every builder brief says: "Do not open or search github.com/vorssaint or any copy of its source."
  • Identity: Notifi has its own name, icon, colours and branding. No Vorssaint names, art or wording in the UI. Vorssaint's TRADEMARKS.md reserves its name, logo, icon and trade dress. Motion is behaviour, so it is matched (section 2b).
  • Record: each spec file has a Sources: line listing the public docs it came from.

2b. Motion: same animation style

  • Where it comes from: the spec agent records Vorssaint in use (on a Mac, or from window-switcher.gif, the site and release videos) and steps through it frame by frame. Nobody reads its source for this.
  • What it writes: spec/motion.md, one row per animation: what moves (opacity, scale, position, blur, height), how long it takes, the curve (spring stiffness and damping, or the easing), any overshoot, and the stagger between items. It covers the tray panel opening and closing, panel tab switches, the app switcher showing and moving its selection, the Top Pill growing and shrinking, toasts, the command bar, the radial menu, the shelf, snap previews, the capture selector, hold-to-quit progress, list reorder and toggle switches.
  • How it is built: one motion token file (ui/motion.ts) holds every duration and spring, named by role (panelOpen, selectionMove …). Components only use tokens. Springs use Svelte's built-in spring and tweened stores (no extra library). CSS transitions use linear() easing generated from the same springs, so CSS and JS feel the same.
  • Windows that animate: our own overlay windows are transparent and frameless, and they animate their contents, not the OS window, so motion stays smooth on Windows, X11 and Wayland. Moving other apps' windows (snapping) follows the OS's own animation. Notifi draws an animated snap preview overlay to match the style.
  • Reduced motion: follows the OS setting (Windows "Animation effects", GNOME/KDE reduce-animation), and has its own switch on the settings page.
  • Check: each phase records Notifi's animations at 60 fps and compares them side by side with the Vorssaint reference clips before release.

4. Phases and checklist

Phase 0: Foundation

  • git init, main branch, MIT LICENSE, README.md, RELEASE_NOTES.md
  • Tauri 2 shell: tray icon and menu, single instance, autostart, no focus steal in test runs
  • Settings store (defaults, JSON, change events) and settings page; one section per feature, each with an on/off switch ("install only what you use")
  • Keybind registry with a capture widget; global hotkeys (Win: RegisterHotKey; Linux: X11 grab or GlobalShortcuts portal)
  • Updater: GitHub releases/latest at startup and every 3 h, background download, SHA-256 check, install on click or quit
  • platform crate with runtime backend choice; empty traits for every capability
  • Tray panel (spec/panel.md): tabs for Keep awake, Mixer, System, Network, Storage, Power, Utilities and Controls, with Settings and Quit at the bottom
  • Island (spec/everyday/island.md), moved up from Phase 6: resting pill, live activities, Now Playing, module grid, Controls, orbit buttons, settings page with a layout editor
  • Permissions page
  • CI: Windows .msi, Linux .AppImage + .deb + .rpm
  • .run/Main Run.run.xml and .run/Dev Run.run.xml
  • Spec agent writes spec/ for every feature
  • Spec agent writes spec/motion.md from recordings; ui/motion.ts token file built from it

Phase 1: Daily core

  • Clipboard history, auto clear, paste as plain text, Clean URL
  • Text snippets (searchable menu first, typed triggers in phase 4)
  • Command Bar (apps, windows, files, clipboard, calculator, units, emoji, scripts)
  • Quick toggles, quick panel, scratchpad
  • System monitor (CPU, memory, battery, network, GPU basics), tray readouts, alerts
  • Keep awake (basic)

Phase 2: Sound

  • Volume mixer, per-app output, output switcher, microphone tools, media-key app blocker

Phase 3: Windows

  • GNOME extension and KWin scripts
  • Window layouts and snapping, app switcher, quit on close, quit/close protection

Phase 4: Keyboard and mouse

  • Input layer (hooks / evdev + uinput)
  • Scrolling features, acceleration, focus follows mouse, button remaps, click filter, key debounce, Super key, typed snippet triggers, app exclusions

Phase 5: Capture

  • Capture selector, screenshot + editor, pin, scrolling capture, OCR, QR, color picker
  • Recording + editor, media tools, camera preview

Phase 6: Top Pill and extras

  • Top Pill (media, timers, downloads, calendar, notifications where possible)
  • AI agents panel
  • Radial menu, Cleaning Mode, shelf

Phase 7: App management

  • App updates, package manager, uninstaller, cleaner, messaging downloads, port manager, AppImage installer

Phase 8: Energy, display and sensors

  • Displays and DDC brightness, software dimming, lid-closed keep awake, Bluetooth on sleep
  • Privileged helper; temperatures and fan control (Linux first, Windows beta)

5. Risks

  • Windows sensors and fans: the usual free driver (WinRing0) is now flagged by Defender. Plan: Linux first; on Windows, show sensors only if the user already runs LibreHardwareMonitor (read its data), never ship a driver ourselves.
  • Volume boost past 100% on Windows: needs an APO such as Equalizer APO. Plan: support boost only when one is installed.
  • Wayland: global input needs the input group, and window control needs our extension/scripts. The permissions page walks the user through it. Other compositors (Sway, Hyprland) are best effort.
  • Windows notification mirroring needs a packaged (MSIX) app identity. Skipped unless we ship MSIX as well.
  • Size: ~60 features to build. Each phase is its own release.

6. New dependencies to approve

All free and open source: Tauri 2, windows crate, sysinfo, zbus (D-Bus), libpulse/pipewire bindings, evdev, x11rb, rxing, Tesseract, FFmpeg, image, a front-end framework (Svelte recommended, it's small).
